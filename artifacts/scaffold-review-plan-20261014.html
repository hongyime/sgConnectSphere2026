02

Plan and decision rules

1 · Freeze the source set

  • Record the audit commit and date. Use docs/testing/cases/ as acceptance-case authority; use the latest dated workbook as its generated snapshot.
  • Check whether the legacy undated workbook consumed by scripts/tc_coverage_audit.py has been refreshed from that snapshot. Do not edit any workbook by hand.
  • Use the Release 1 backlog for selected release requirements, the product backlog for wider scope, and BDR decisions for accepted clarifications. Keep one row per TC_ID.

2 · Find scaffold candidates

Search runnable test roots, then inspect each match in context. The active Playwright scaffold is in tests/e2e/; frontend and backend tests also count. Exclude the historical reference copy in docs/testing/frontend-verification-scaffold-v5/.

rg -n 'test\.fixme|test\.skip|test\.todo|describe\.skip|it\.skip|xit\(|xtest\(' tests frontend backend -g '*.{spec,test}.{ts,tsx,js,jsx}'rg -n 'TODO|FIXME|placeholder|Not implemented|expect\(true\)\.toBe\(true\)|expect\(false\)\.toBe\(true\)' tests frontend backend -g '*.{spec,test}.{ts,tsx,js,jsx}'

Classify each hit: deliberate fixme specification, conditional/environment skip, pending test, empty/trivial placeholder assertion, or ordinary TODO. Do not equate every test.skip with an abandoned scaffold.

3 · Cross-reference cases and code

  1. Enumerate TC_IDs and story/AC references from canonical case Markdown, then compare them with exact TC_ID matches in active and skipped/fixme test declarations.
  2. Report three sets: catalogue IDs with active test references, IDs mentioned only in scaffolds/skips, and catalogue IDs with no direct test-code reference. Also flag code IDs missing from the current catalogue and duplicate references.
  3. For every apparent “no reference,” inspect active assertions and traceability comments. The current auditor matches IDs in test titles; it can miss behavioral coverage under a title without a TC_ID.
  4. Capture the source case, acceptance criterion, candidate code/test locations, current assertion quality, status evidence, proposed disposition, rationale, owner/trigger, and links in a review matrix.

4 · Establish story status

  • Backlog + BDR: identify accepted scope, dependencies, planned sprint, and whether a case is current, future, superseded, or cross-cutting.
  • Jira: read the issue status when the operator has provisioned access; treat Jira as a workflow mirror and record “not checked” if unavailable. Do not change Jira during the audit.
  • GitHub: search story/Jira keys in branches and PRs; inspect open, draft, merged, review, and required-check evidence plus the files actually changed. A merged PR alone does not prove the whole story is Done.
  • T-65: inspect run records for observed execution and skipped/fixme notes. A historical PASS/SKIP does not establish current source coverage or current story status.
  • Resolve contradictions against canonical Markdown and the Definition of Done. A Done story stays Done; any missing work becomes a new follow-up story.

Disposition criteria

DispositionUse whenRequired handling
Implement / convertThe accepted case is in active selected scope, the behavior exists or is being delivered, and review finds no equivalent credible assertion. Also use for a verified acceptance gap after status review.Turn the scaffold into assertions against real behavior; retain TC_ID, story, AC and implementation traceability. For a Done story, create a follow-up story rather than reopening it. Meet the DoD and record cited test evidence under T-65.
Remove / retireThe scaffold duplicates an active test that demonstrably covers the same criterion, or canonical scope has been retired/superseded by an accepted decision.Remove duplicate code only after mapping coverage. Retire a case in canonical Markdown first, then regenerate dated exports, reconcile the legacy workbook input, and regenerate tc-coverage.md. Keep history and explain the decision.
Leave as-isThe story is future/unselected, blocked by a dependency or unresolved decision, or an explicit conditional skip reflects environment limits. An unreferenced case may also be valid cross-cutting coverage handled by shared tests.Keep the case/scaffold and state the blocker, status source, owner or trigger, and next review point. If behavior is covered under another title, add/retain traceability rather than inventing a redundant test.

Prioritization

  1. P0 · Release and safety gaps: accepted authentication, authorization/client isolation, destructive updates, audit/data integrity, transaction/migration, and other high-impact criteria whose story is claimed Done or whose PR is merged but lack credible active assertions or required evidence. For Done stories, file follow-up work without changing the old status.
  2. P1 · Current sprint / In Progress / review-ready PR: fixmes and catalogue-only cases needed to validate acceptance before merge or Sprint Review. Include review requests/changes and CI results in the triage.
  3. P2 · Previously delivered stories with traceability gaps: first determine whether equivalent tests already assert the behavior; fix trace links or create a follow-up story for a real acceptance gap.
  4. P3 · Future, blocked, cross-cutting, or superseded cases: document the reason and trigger, or retire only through the canonical source. Do not promote work solely to improve inventory percentages.

Use the current epic counts to choose where to inspect first, not to auto-rank: E08 and E10 show no active TC_ID-linked cases in the inventory; E09 and E06 have many scaffold rows. Verify their story status before assigning priority.

Evidence and environment: no test run is needed to create this plan. When a later run is used as PR/DoD/demo evidence, add one T-65 session record. Do not start Docker Desktop or write/reset shared Supabase. If database verification is later needed, use the repo-supported isolated local loopback PostgreSQL workflow or GitHub Actions’ isolated PostgreSQL service; read docs/testing/supabase-test-schema.md before any Supabase test and observe its rollback-only limit.

Sources: source-of-truth rules, current generated coverage inventory, coverage audit implementation, test reference and traceability guidance, T-65 run-record policy, Jira workflow, and the Definition of Done.
