Validate manual Remarks on post-policy run records

Make the T-65 validator require an observed result for each row in a new manual run, while grandfathering pre-policy records and keeping automated records unchanged.

Rule overview

Use the frontmatter run timestamp as the policy boundary. Existing validation already requires Singapore time and checks that the filename date matches that timestamp's calendar date.

Implementation details

Files in the implementation PR

  • scripts/check_test_run_records.py — cutoff constant and per-row validation context.
  • tooling/tests/test_run_records.py — boundary, remarks, and run-type coverage.
  • docs/testing/runs/README.md — exact effective timestamp and validity rule.
  • docs/testing/README.md — keep the high-level catalogue/execution explanation aligned and link to the detailed rule.

Do not edit existing files in docs/testing/runs/, including the 14 blank manual rows in the two 2 October records.

Remarks validity

  • Require at least one non-whitespace character.
  • Reject a cell whose entire content is only the matching outcome token, case-insensitively; “PASS” alone is not actual-result evidence.
  • Do not impose a character count or rigid format. A validator cannot establish whether free text truthfully describes what the tester observed; human review still checks that.

Scope and edge cases

  • Apply only when run_type: manual and frontmatter date is at or after the cutoff.
  • Check every valid result row. A manual MULTIPLE row also needs a substantive remark, such as the aggregate count and evidence link.
  • Automated rows may still have blank Remarks. Do not infer manual status from environment or scope.
  • regression remains unchanged because the schema treats it as a separate run_type; broadening this needs a policy decision.
  • Malformed or missing dates already fail current validation. Do not fall back to the filename for the policy decision.

Validator shape

Pass a boolean or record context into _validate_table indicating that manual Remarks are required. Keep Markdown parsing and current structural checks in the same path; add the Remarks error only after a row has the expected four cells.

Use the parsed timezone-aware frontmatter timestamp, after its Singapore offset is validated. The filename date continues to be checked against that timestamp's date.

Sources: T-65 record schema, testing documentation, and source-of-truth policy.

Tests and rollout

Tests to add

  1. Manual blank Remarks one second before cutoff is accepted; at the cutoff it fails.
  2. Manual whitespace-only Remarks and outcome-only Remarks fail after cutoff.
  3. Manual Remarks with observed-result text pass after cutoff.
  4. Pre-cutoff manual blank Remarks pass, including an October 2-shaped fixture.
  5. Post-cutoff automated blank Remarks remain accepted.
  6. Manual MULTIPLE is checked; a populated aggregate result passes.
  7. Existing outcome, column-count, and filename-date validation continues to fail on malformed input.

Safe rollout

  1. Before enabling the rule, inventory all manual rows around the cutoff and confirm no post-cutoff manual row is blank. Current audit found the 14 blanks only in the two October 2 records.
  2. Add the cutoff-based check and synthetic unit cases. Leave all existing run files byte-for-byte unchanged.
  3. Run the focused tooling tests and python scripts/check.py; the latter runs the validator and repository-tooling tests, not application/database suites.
  4. Record any verification run used as PR evidence as one new T-65 session file. Do not rewrite an existing session file.
  5. Let CI run the same repository check. No Docker Desktop, Supabase access, reset, or database writes are needed.
Known limits

This is a presence and low-effort placeholder check, not semantic verification. A short but real result may be valid; reviewers remain responsible for confirming that Remarks state what was observed. The cutoff applies to the session timestamp, not the later Git commit date of a backfilled record.

The 7 October policy was added by PR #223, which explicitly says the rule applies to new runs and leaves prior records untouched. No tests were run for this plan.
