## E14-S02

### TC_E14S02_01 — Verify that an event status change should be recorded with the actor, action, affected event, and time

- **Sprint**: 3
- **AC reference**: E14-S02 - Scenario 1 (Status change recorded; T-75, T-76)
- **Type**: 2 - Happy Path

#### Pre-conditions

Seeded request "EVT-2003 Client B Isolation Event" has status "Under Review" and is assigned to coord_b@connectsphere.com, who is permitted to view and approve it

#### Test steps

1. As coord_b@connectsphere.com, approve the request (status -> Approved)
2. Open the approved event's existing detail page as that Coordinator
3. Locate the status-change entry in its Activity log
4. Compare the displayed actor, action and timestamp with the completed change and affected event

#### Test data

Event: EVT-2003 Client B Isolation Event | Action: Approve

#### Expected result

An entry is recorded with actor = coord_b@connectsphere.com, action = "Status changed to Approved", event = EVT-2003 Client B Isolation Event, and a timestamp; the Event Coordinator can read it on that event under existing access rules, without an Administrator role or global audit screen

### TC_E14S02_05 — Verify that any attempt to edit or delete an activity log entry should be refused

- **Sprint**: 3
- **AC reference**: E14-S02 - Scenario 5 (Log entries immutable; T-75, T-76)
- **Type**: 4 - Negative

#### Pre-conditions

A log entry exists: Event = EVT-2003 Client B Isolation Event, Action = "Status changed to Approved", Actor = coord_b@connectsphere.com (created in TC_E14S02_01 or an equivalent independent fixture in a disposable test database)

#### Test steps

1. As an Event Coordinator permitted to view the event, open its Activity log
2. Confirm no edit or delete control is offered for the entry
3. For each existing application role (event_organiser, event_coordinator, venue_staff, technical_support_staff and attendee), attempt direct API update and delete requests against the entry
4. As the database test harness, attempt UPDATE and DELETE of that entry through the application database connection in separate transactions
5. Read the original entry after each refused attempt to confirm its contents and row remain unchanged

#### Test data

Target log entry: Event = EVT-2003 Client B Isolation Event, Action = "Status changed to Approved" | Attempted edit: Action -> "Status changed to Rejected"

#### Expected result

All update and delete attempts are refused. Unsupported API methods or routes may return 404/405; protected mutation routes must reject unauthorised requests. No response may represent a successful mutation. The database rejects both operations and the entry remains unchanged. No Administrator role is required.

### TC_E14S02_08 — Verify that access-denial entries should not be shown in the event Activity log a Coordinator reads

- **Sprint**: 3
- **AC reference**: E14-S02 - Scenario 1 (Status change recorded; access-denial entries not shown; T-75)
- **Type**: 3 - Cross-cutting (data isolation)

#### Pre-conditions

Event EVT-2003 belongs to Client B, is Under Review and is assigned to coord_b@connectsphere.com; organiser_a@clienta.com belongs to Client A; the database is a disposable test database seeded with `npm run db:seed:test --workspace backend`

#### Test steps

1. As organiser_a@clienta.com, attempt to open EVT-2003 directly and confirm the request is refused
2. As the tester, confirm in the test database that an "Access Denied" row naming organiser_a@clienta.com now exists for that attempt
3. As coord_b@connectsphere.com, approve EVT-2003 so the log also holds a status-change entry
4. As coord_b@connectsphere.com, open EVT-2003's Activity log
5. Check every entry shown

#### Test data

Refused user: organiser_a@clienta.com (Organiser A, Client A) | Event: EVT-2003 (Client B) | Reader: coord_b@connectsphere.com

#### Expected result

The Activity log shows the status-change entry from step 3 and no "Access Denied" entry; neither "Organiser A" nor organiser_a@clienta.com appears anywhere in the log

## E14-S03

### TC_E14S03_01 — Organiser reads an edited date/time value in Singapore time

- **Sprint**: 3
- **AC reference**: E14-S03 - Scenario 1
- **Type**: 2 - Happy Path

#### Pre-conditions

Planned, not executed. A disposable local event accessible to its Organiser has a controlled audit fixture for an edited startAt value; use the existing Organiser Activity log, not a new viewer.

#### Test steps

1. Set the browser timezone to a non-Singapore timezone in the test environment.
2. Sign in as the Organiser and open the event's Activity log.
3. Locate the edited start value and compare it with shared formatDate(value, true).
4. Reload and verify the displayed value remains the same.

#### Test data

field_changed: startAt; new_value: 2026-10-15T09:30:00Z; browser timezone: UTC.

#### Expected result

The displayed edited value represents 15 October 2026 at 17:30 Singapore time (5:30 pm in the helper's format), on the same calendar date, not raw UTC or browser-local time. The Organiser view is not required to add a previously absent old-value display.

### TC_E14S03_06 — Formatting preserves immutable UTC evidence and existing reader access

- **Sprint**: 3
- **AC reference**: E14-S03 - Scenario 5
- **Type**: 3 - Cross-cutting (data isolation)

#### Pre-conditions

Planned, not executed. A disposable local database contains an event for one client, its assigned Coordinator, a different-client Organiser, an unassigned Coordinator and an existing access-denial row. A controlled tester snapshots its audit rows read-only.

#### Test steps

1. Snapshot old_value, new_value, occurred_at, actor and action for the edited date/time row.
2. As the permitted Organiser and assigned Coordinator, view and reload the existing log.
3. Compare the stored values with the snapshot and confirm neither view offers edit/delete controls.
4. Attempt existing direct read routes as the different-client Organiser and unassigned Coordinator.
5. Verify event logs still exclude access-denial entries; use the existing TC_E14S02_05 controlled mutation checks for immutability regression.

#### Test data

Stored UTC new_value: 2026-10-15T09:30:00Z; unchanged old_value and occurred_at; unrelated client and unassigned Coordinator; immutable audit row.

#### Expected result

Permitted reads format only the presentation: the original stored UTC values, occurrence time, actor and action are unchanged. Existing mutation refusals remain in force, unauthorised readers remain refused without event data, and denial entries stay hidden. No new viewer, permissions or history feature is introduced.
