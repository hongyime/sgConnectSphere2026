# ConnectSphere backlog

This directory holds the canonical product backlog for ConnectSphere. It is
authoritative. The Excel workbook (`docs/CONNECTSPHERE BACKLOGS CAA
<DDMMYYYY>.xlsx`) is a generated export produced by
`scripts/export_backlog_xlsx.py` from these Markdown files; when the two
disagree, Markdown wins.

Rationale for the split: Markdown supports 3-way git merges, produces
reviewable diffs, and lets agents edit a single story precisely without
touching the whole workbook. Architecture and backlog decisions are also
authoritative in `docs/adr/` and `docs/bdr/`, per repository decision 0005.
Word copies are historical/generated handoffs.

For completed work, contributors, review gaps and Jira reconciliation, read
the [Sprint 1 delivery ledger](sprint-1-delivery.md). It records progress
against these requirements without changing the original sprint estimates.

## File layout

Stories are grouped by epic. Each epic has two files:

- `docs/backlog/release-1/E<xx>-<slug>.md` — stories scheduled in Release 1.
- `docs/backlog/product/E<xx>-<slug>.md` — the full imported product view.

Within each file, stories appear in Story ID order (`E01-S01`, `E01-S02`, ...).
The two files exist because the Release 1 slice and the wider product backlog
are two views of the same product, and the workbook stores them on separate
sheets. Release stories also appear in the imported product view. Count each
story ID once; use `release-1/` for a selected story's release requirements,
estimate and planned sprint. Reconcile its product view when requirements
change. The 20 September audit found 71 distinct stories, including 47 in
Release 1; the two views must not be summed.

## Story format

Every story is a Markdown block that starts with a level-two heading in
this exact form:

```markdown
## E<xx>-S<yy> — <Story title>

- **Sprint**: Sprint 1 | Sprint 2 | Sprint 3 | Sprint 4 | (empty for future)
- **Points**: <integer or empty>
- **BDR references**: <comma-separated codes, e.g. `C-30, T-38, O-02`>
- **Owner**: <optional pair or individual>

### User story

<As a ..., I want ..., so that ...>

### Acceptance criteria

#### Scenario 1 — <short label>

<Given/When/Then paragraph or short bullet list>

#### Scenario 2 — <short label>

<...>

### Checklist

- <observable checklist item>
- <observable checklist item>
- ...
```

Rules that this format enforces:

- Every story has a Story ID and a title.
- Every story has a `User story` section with the As-a / I-want / So-that
  form. If the workbook row was blank on user story, the Markdown says
  `_No user story recorded._` explicitly rather than leaving a gap.
- Every story lists acceptance criteria as numbered Scenario sub-headings.
  Multi-line scenarios in Gherkin form (Given / When / Then) stay as
  Gherkin.
- Every story ends with a Checklist of observable outcomes. If none was
  recorded in the workbook, the section is present but empty.
- Metadata (Sprint, Points, BDR references, Owner) is a Markdown
  definition-style bullet list at the top of the story. Missing values are
  represented as an empty string, not omitted, so the export can
  round-trip cleanly.

Rules the format does NOT try to enforce:

- Markdown lists inside scenarios may nest freely. Reviewers should
  prefer flat lists but the export tolerates nesting.
- Prose inside Given/When/Then may use ordinary sentences. Strict Gherkin
  is not required.
- Cross-references to other stories or BDR entries are inline text tokens
  (e.g. `see T-52`, `blocks E06-S06`), not Markdown links, so files stay
  readable even if link URLs change later.

## When you change a story

1. Edit the Markdown block directly. Do not open the workbook and re-run
   the conversion script from scratch — the Markdown is now the source.
2. If the change affects a derivative (C4 diagrams, user flows, test
   cases, Jira), include the derivative update in the same PR, or note in
   the PR body which derivatives you checked and why no update was
   needed.
3. If the change affects backlog scope, points, sprint assignment, or
   priority, also add or amend the matching entry in
   `docs/bdr/` (T-52 pattern).

The workbook is regenerated by running
`python scripts/export_backlog_xlsx.py`. Regeneration is a manual step —
usually before a Jira import or when someone wants to open the backlog in
Excel. CI does not auto-regenerate the workbook.

## When you add or retire a story

- Add: append the new story block to the correct epic file in Story ID
  order. Do not create a new file unless a new epic is being added.
- Retire: prefix the story title with `[RETIRED — <reason>]` and leave
  the block in place. Do not delete retired stories; they are how future
  readers know a story existed and why it was withdrawn (see ADR-004 and
  ADR-005 in the decision records for the pattern).

## Automated round-trip

The conversion is two-way:

- `scripts/one_shot/backlog_xlsx_to_md.py` seeded these files from the
  workbook at CAA 140926. It is one-shot and not part of the day-to-day
  workflow.
- `scripts/export_backlog_xlsx.py` reads these Markdown files and writes
  `docs/CONNECTSPHERE BACKLOGS CAA <DDMMYYYY>.xlsx` for Jira CSV import or
  reviewer convenience. It is idempotent.

A tooling test under `tooling/tests/test_backlog_roundtrip.py` runs both
directions against a fixture Markdown tree and asserts fields survive the
round trip.
